    QuickNotes v1.5.7 — Comprehensive User Manual & Technical Reference

    ⚡ Quick Start: First-Time Installation & Default Credentials

    QuickNotes is packaged as ready-to-deploy Docker containers. No local compilation or manual database seeding is required.

    1. Default Login Credentials

    The system is pre-configured with two standard accounts initialized automatically on first startup:

    Role Username Default Password Access Tier & Capabilities
    👑 App Owner owner quicknotes_owner_password_2026 Full Administrator: Cloud Storage configuration (Google Drive, S3, R2, B2), Backups & Disaster Recovery, User Management, API Key generation, and Note Deletion.
    🤖 API User api_user quicknotes_api_password_2026 Restricted AI Agent Tier: Create/edit notes, manage labels, and upload attachments. Restricted from deleting notes or modifying system settings.
    Where are default credentials configured?
    Default accounts are defined in server/src/db/migrate.ts and automatically created during the database schema migration on initial launch. In the Web UI, 1-Click Quick Login buttons in the sign-in modal allow immediate access. You can update passwords or create new users at any time under Settings → Users.

    2. First-Time Docker Compose Deployment

    Save the following docker-compose.yml file to any folder on your computer and run docker compose up -d:

    services:
  postgres:
    image: postgres:18-alpine
    container_name: quicknotes_postgres
    restart: unless-stopped
    environment:
      POSTGRES_DB: quicknotes_db
      POSTGRES_USER: quicknotes_user
      POSTGRES_PASSWORD: quicknotes_password_2026
    volumes:
      - quicknotes_pgdata:/var/lib/postgresql
    ports:
      - "5434:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U quicknotes_user -d quicknotes_db"]
      interval: 3s
      timeout: 3s
      retries: 10

  app:
    image: ghcr.io/uri-travoski/quicknotes:latest
    container_name: quicknotes_app
    restart: unless-stopped
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      PORT: 3000
      DATABASE_URL: postgresql://quicknotes_user:quicknotes_password_2026@postgres:5432/quicknotes_db
      NODE_ENV: production
      UPLOAD_DIR: ./uploads
      # Set your initial admin credentials here:
      DEFAULT_OWNER_USERNAME: owner
      DEFAULT_OWNER_PASSWORD: quicknotes_owner_password_2026
      DEFAULT_API_USERNAME: api_user
      DEFAULT_API_PASSWORD: quicknotes_api_password_2026
    volumes:
      - quicknotes_uploads:/app/uploads
      - quicknotes_backups:/app/backups
    ports:
      - "3000:3000"

volumes:
  quicknotes_pgdata:
    driver: local
  quicknotes_uploads:
    driver: local
  quicknotes_backups:
    driver: local

    Once started, access the application:

    • On this machine: http://localhost:3000
    • On your local network (phones, tablets, laptops): http://<LOCAL_IP>:3000 (e.g. http://192.168.68.101:3000)
    📱 Mobile & PWA Installation: Open http://<LOCAL_IP>:3000 on Safari (iOS) or Chrome (Android) and tap "Add to Home Screen" to install QuickNotes as a native mobile app.

    1. System Architecture & Storage Model

    QuickNotes utilizes a decoupled client-server architecture engineered for sub-millisecond response times even with thousands of rich notes:

    • React Frontend (Port 3000): Vite, Tailwind CSS, Lucide Icons, and progressive scroll rendering.
    • Express Backend (Port 5000): Node.js 26 REST API with Sharp for automated thumbnail generation and Multer for file uploads.
    • PostgreSQL 18 Database: Stores structured text, note contents, tags, hierarchy tree, checklists, and attachment metadata pointers.
    • Binary Storage (Local or Cloud): Stores actual binary assets (images, videos, documents, and thumbnails) on Local Disk (/app/uploads), AWS S3, Cloudflare R2, Backblaze B2, or Google Drive.
    Database vs Binary Separation: PostgreSQL stores metadata (~3ms queries). The heavy binary files reside in your cloud bucket. When you restore the database on a fresh server, all attachment links immediately connect without copying gigabytes of files.

    9. Settings: Storage (Local Disk, AWS S3, Cloudflare R2, Backblaze B2, Google Drive)

    QuickNotes features a pluggable, multi-provider storage architecture that completely decouples text metadata from heavy binary files (images, videos, PDFs, spreadsheets, archives).

    How Storage Works Under the Hood

    • Upload Pipeline: When you upload a file or paste an image from your clipboard (Ctrl+V), the Express backend receives the stream via Multer, uses Sharp to generate an optimized WebP thumbnail, and writes both the original asset and thumbnail to the active storage provider.
    • Database Record: The PostgreSQL attachments table records the file's unique object key (filename), thumbnail key, original name, MIME type, file size, dimensions, and the storage_provider used at the time of upload.
    • Zero-Lock-in Provider Tracking: Each attachment record stores its own storage_provider. If you upload 100 images to Local Disk and later switch to Cloudflare R2, existing attachments continue to stream from Local Disk while new attachments go to R2. Nothing breaks!
    • Streaming & Lightbox: When viewing notes or opening the full-screen Lightbox, the server streams the file directly from your cloud bucket or local disk using authenticated signed streams.

    Step-by-Step Setup Guides for Storage Providers

    Option A: Local Disk Storage (Default)

    • Storage Path: Files are saved to /app/uploads with thumbnails in /app/uploads/thumbnails.
    • Docker Volume: Persisted across container restarts using the named volume quicknotes_uploads.
    • How to use: No configuration required. Click Test Read/Write to verify filesystem permissions, then click Set Active.

    Option B: AWS S3

    1. In the AWS Console, create an S3 bucket (e.g. my-quicknotes-prod).
    2. Create an IAM User with programmatic access and attach the AmazonS3FullAccess policy (or a custom policy scoped to your bucket ARN).
    3. In Settings → Storage → S3-Compatible, enter:
      • Endpoint URL: Leave blank (AWS S3 uses standard regional endpoints automatically).
      • Bucket Name: my-quicknotes-prod
      • Region: e.g. us-east-1, eu-west-1
      • Access Key ID: Your IAM Access Key
      • Secret Access Key: Your IAM Secret Access Key
    4. Click Test Connection to run a live read/write latency benchmark.
    5. Click Save, then click Set Active.

    Option C: Cloudflare R2 (Zero Egress Fees)

    1. In the Cloudflare Dashboard, go to R2 Object Storage and click Create bucket (e.g. quicknotes-r2).
    2. Under R2 Account Details, click Manage R2 API Tokens → Create API Token with Object Read & Write permissions.
    3. Copy your Account ID, Access Key ID, and Secret Access Key.
    4. In Settings → Storage → S3-Compatible, enter:
      • Endpoint URL: https://<your-account-id>.r2.cloudflarestorage.com
      • Bucket Name: quicknotes-r2
      • Region: auto
      • Access Key ID: Your R2 Access Key ID
      • Secret Access Key: Your R2 Secret Access Key
    5. Click Test Connection, then Save and Set Active.

    Option D: Backblaze B2

    1. In Backblaze B2, create a bucket with Private default visibility.
    2. Under App Keys, generate an Application Key with read/write access to that bucket.
    3. Note the S3 Endpoint listed on your Bucket Details page (e.g. https://s3.us-west-004.backblazeb2.com).
    4. In Settings → Storage, enter Endpoint URL, Bucket Name, Region (e.g. us-west-004), Key ID, and Application Key.
    5. Click Test Connection, Save, and Set Active.

    Option E: Google Drive (OAuth 2.1 with PKCE & Service Account)

    QuickNotes offers two distinct authentication modes for Google Drive: 1-Click OAuth 2.1 with PKCE (recommended for personal accounts) and Service Account (.json) (for automated enterprise workflows).

    Method 1: 1-Click OAuth 2.1 Sign-In with PKCE (Recommended)
    1. In Google Cloud Console, create a project and enable the Google Drive API v3 (under APIs & Services → Library).
    2. Under OAuth consent screen, select External, fill in app name/emails, and add scopes:
      • .../auth/drive.file (Per-file access for note attachments)
      • .../auth/userinfo.email (Displays connected account identity)
      Note: While in Testing status, add your Google account email under Test Users.
    3. Under Credentials → Create Credentials → OAuth client ID, choose Web application:
      • Authorized JavaScript origins: http://localhost:3000 (or your domain e.g. https://notes.yourdomain.com)
      • Authorized redirect URIs: http://localhost:3000/api/storage/gdrive/oauth/callback (Copy from Settings → Storage → Google Drive)
    4. In Settings → Storage → Google Drive → OAuth 2.1:
      • Paste your Google Client ID and Google Client Secret.
      • Click the blue "Sign in & Connect Google Drive" button.
      • Authenticate in the Google popup window. The window will automatically close and show your connected Google email with a green Connected badge.
    5. Click Test Connection to verify live connection latency and storage quota (e.g. Sam Dabhi (email@domain.com) (58.9 GB / 5120 GB used)).
    6. (Optional) Specify a custom Destination Folder ID or leave as root.
    Method 2: Google Service Account (.json)
    1. In Google Cloud Console, go to IAM & Admin → Service Accounts and create a service account.
    2. Generate and download a JSON key for that service account.
    3. In Google Drive, create a destination folder and Share that folder with the service account's email (granting Editor permissions). Copy the Folder ID from the URL.
    4. In Settings → Storage → Google Drive → Service Account (.json):
      • Click Upload Service Account JSON File or paste the JSON text directly.
      • Enter the destination Folder ID.
    5. Click Test Connection, then Save and Set Active.
    Storage Best Practices (What to Do):
    • Always click Test Connection before clicking "Set Active" to confirm credentials and network latency.
    • Use dedicated IAM or API tokens with permissions restricted strictly to your QuickNotes bucket.
    • Enable CORS on your S3/R2 bucket if configuring direct client uploads.
    Storage Critical Gotchas (What NOT to Do):
    • DO NOT delete or rename your cloud bucket: Existing notes store unique object keys pointing to that bucket. Deleting the bucket will break image and document links.
    • DO NOT delete the quicknotes_uploads Docker volume: If you are using Local storage, deleting the Docker volume deletes your uploaded files.
    • DO NOT include trailing slashes in Endpoint URLs: Use https://<account>.r2.cloudflarestorage.com without a trailing /.
    • DO NOT enter an Endpoint URL for standard AWS S3: Leave it blank so the AWS SDK automatically constructs the correct regional endpoint.

    10. Settings: Backups & Disaster Recovery

    QuickNotes includes a built-in automated backup and disaster recovery engine designed to protect your notes, tags, checklists, and attachment metadata against data loss.

    How Backups Work Under the Hood

    • Native PostgreSQL Dump: When a backup is triggered, the backend executes pg_dump inside the PostgreSQL container, capturing the complete relational schema, all tables (notes, tags, note_tags, attachments, users, storage_configs), sequences, foreign keys, and indexes into a self-contained database_dump.sql.
    • Metadata Manifest: The engine generates a manifest.json containing the schema version, total note count, tag count, attachment count, timestamp, and storage provider metadata.
    • Standard ZIP Packaging: The SQL dump and manifest are packaged into a standard compressed .zip archive (e.g. quicknotes_backup_2026-08-21T05-11-50-861Z.zip).
    • Cryptographic SHA-256 Integrity Verification: The engine calculates a cryptographic SHA-256 checksum of the entire archive and stores it in the backups table. Every backup is automatically verified upon creation and can be re-verified at any time with the ShieldCheck button.

    Step-by-Step Guide: How to Create a Backup

    1. Navigate to Settings (top-right menu) → Backups.
    2. Select the Backup Storage Target: Local Disk, S3 Cloud Bucket, or Google Drive.
    3. Click the green Run Backup Now button.
    4. The process completes in ~1-3 seconds. The new backup appears in the Backup History table with a green "Verified & Valid" badge.
    5. Click the blue backup filename link (e.g. quicknotes_backup_2026-08-21T05-11-50-861Z.zip) to download the archive directly to your local computer or offline storage drive.

    Step-by-Step Guide: How to Restore a Backup (3 Methods)

    Method 1: Instant In-App Restore (from Backup History)

    1. In Settings → Backups, scroll to the Backup History list.
    2. Find the backup you wish to restore.
    3. Click the Restore icon (↺ circular arrow) next to that backup row.
    4. Read the confirmation dialog and click Restore Backup.
    5. The backend extracts database_dump.sql, executes the restore inside a transaction, and automatically reloads all notes, tags, and settings.

    Method 2: In-App Upload & Restore (from External .zip File)

    1. In Settings → Backups, locate the Restore from External Archive File card.
    2. Click Upload & Restore (.zip) and select any previously downloaded quicknotes_backup_*.zip file from your machine.
    3. Confirm the dialog. The server uploads the archive, validates the SHA-256 checksum and manifest, restores the PostgreSQL database, and refreshes the application.

    Method 3: Full Disaster Recovery on a Fresh Server / Host

    If your entire server was destroyed or you are migrating to a brand-new cloud VPS, follow these disaster recovery steps:

    1. Deploy QuickNotes on the new server using Docker: 
      git clone <repo-url> && cd QuickNotes
docker-compose up -d
    2. Extract your backup archive on your local terminal: 
      unzip quicknotes_backup_2026-08-21.zip
# Extracts: database_dump.sql and manifest.json
    3. Restore the SQL dump into the PostgreSQL container: 
      docker exec -i quicknotes_postgres psql -U quicknotes_user -d quicknotes_db < database_dump.sql
    4. Ensure your cloud storage bucket credentials (AWS S3, Cloudflare R2, Backblaze B2, Google Drive) are configured in .env or via Settings.
    5. Open http://<server-ip>:3000 in your browser. All your notes, hierarchical tags, and cloud attachments are 100% restored and fully functional!
    Backup Best Practices (What to Do):
    • Download backup .zip files regularly to an external hard drive or secure cloud storage.
    • Always verify the backup status shows "Verified & Valid" with a valid SHA-256 hash.
    • Store your cloud bucket credentials securely alongside your database backups.
    • Periodically test a restore on a local or staging environment to ensure disaster readiness.
    Backup Critical Gotchas (What NOT to Do):
    • DO NOT restore a backup while users are actively editing: Restoring completely replaces the current database with the backup snapshot. Any unsaved edits made since the backup was generated will be overwritten.
    • DO NOT manually alter database_dump.sql or manifest.json inside the .zip: Modifying files inside the archive changes its checksum and will trigger a SHA-256 integrity mismatch error upon verification.
    • DO NOT delete your cloud storage bucket after making a database backup: The database SQL dump stores all notes, metadata, and object keys (~2MB), while the heavy images and videos reside in your bucket. Both are required for full disaster recovery.

    12. Settings: Users & Role Permissions

    QuickNotes features a dual-tier permission model designed for personal ownership combined with secure AI agent integration:

    Role Default Username Default Password Permissions & Scope
    👑 Owner owner quicknotes_owner_password_2026 Full Administrator: Can configure Cloud Storage, run/verify/restore Backups, generate API Keys, create/manage Users, change passwords, and permanently delete notes.
    🤖 API User api_user quicknotes_api_password_2026 AI Automation Tier: Designed for AI agents (Claude, Gemini, Cursor). Can create/edit notes, manage labels, and upload attachments. Restricted from deleting notes or accessing Settings.

    Where Credentials are Configured & Managed

    • Initial Setup: Defined in server/src/db/migrate.ts and automatically created during initial database migration.
    • Changing Passwords: Log in as owner, go to Settings → Users, and click "Change Password" next to any user.
    • Creating New Users: In Settings → Users, click "Create User" to add additional accounts.
    • 1-Click Quick Login: The login modal provides instant 1-click buttons for rapid testing and role switching.

    13. Gotchas & What NOT to Do

    Permanent Deletion: Clicking "Delete Forever" or "Empty Trash" permanently removes records. This cannot be undone without a backup.
    Avoid Large Base64 in Text: Do not paste huge base64 strings into markdown text. Always use attachment uploads or clipboard paste (Ctrl+V) for fast thumbnail generation and database performance.
    Cloud Credentials on Restore: When restoring a database on a new server, ensure your storage credentials (S3/R2/B2) match the bucket name so attachments open immediately.

    Creating a Note via Python REST API

    import requests

API_URL = "http://localhost:3000/api/notes"
API_TOKEN = "sk_qn_your_token_here"

payload = {
    "title": "Automated Server Health Check",
    "content": "## System Status\n- [x] CPU Load < 25%\n- [x] Latency: 2.4ms",
    "color": "mint",
    "is_starred": True
}

headers = {"Authorization": f"Bearer {API_TOKEN}", "Content-Type": "application/json"}
response = requests.post(API_URL, json=payload, headers=headers)
print("Created Note:", response.json())
